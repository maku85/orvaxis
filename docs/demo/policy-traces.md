# What stopped the request?

Pick a recorded request to see why it ended the way it did: the route, the policy that made the terminal decision, which stage it belonged to, whether the handler ran, and whether the policy trace was truncated.

<TraceExplorer />

## What the scenarios show

The six single-purpose scenarios separate failures that look alike from the outside:

| Scenario | Status | Terminal decision | Handler | What it teaches |
|---|---|---|---|---|
| Allowed | 200 | none | ran | every policy allowed |
| Denied | 403 | `document-owner` denied | not run | a policy said no; later stages were never reached |
| Policy evaluation error | 500 | `ledger-access` errored | not run | the policy failed to decide; this is a bug, not a denial |
| Validation failed | 422 | none | not run | the schema rejected the body; no policy stopped it |
| Handler error | 500 | none | ran | policies allowed it and the handler failed |
| Trace truncated | 403 | `audit-reader` denied | not run | decisions beyond the limit were dropped, the terminal one was kept |

The multi-tenant set runs the [demo identities and tasks](/guide/multi-tenant-demo) through every combination of five identities (no key, alice, bob, maya and an admin) and four resources: who is stopped by authentication, by the tenant boundary, by task ownership, or by the admin role.

## How the data is produced

The scenarios are **pre-recorded build fixtures generated by running the real Orvaxis request pipeline** in [`examples/policy-diagnostics.ts`](https://github.com/maku85/orvaxis/blob/main/examples/policy-diagnostics.ts), and every fact on the page comes from [`buildRequestReport()`](/reference/core-concepts#request-report). The site build fails if a scenario no longer produces its expected status, outcome, terminal policy and handler result, if a multi-tenant combination disagrees with the [permission matrix](/guide/multi-tenant-demo), or if the generated data contains request values, headers, API keys, denial reasons or error messages. The tests are in [`tests/policyDiagnosticsDemo.test.ts`](https://github.com/maku85/orvaxis/blob/main/tests/policyDiagnosticsDemo.test.ts).

The page is static. The selectors only choose between results generated from the demonstration fixtures (tenants `acme` and `globex`, four users, three tasks); the browser does not call a backend, simulate one, or run any policy. The identities and API keys are demonstration data, not a real authentication system. The explorer reflects the `main` branch, including policy IDs that are not in the published 0.4.0 package.

## Run the same requests locally

Each scenario shows its own copyable command. For example, from a repository checkout:

```bash
git clone https://github.com/maku85/orvaxis.git
cd orvaxis
pnpm install
pnpm exec tsx examples/policy-diagnostics.ts                      # the six single-purpose scenarios
pnpm exec tsx examples/policy-diagnostics.ts policy-error         # one scenario, plus its JSON request report
pnpm exec tsx examples/policy-diagnostics.ts tenant:bob:task-1    # a multi-tenant combination
```

To see a multi-tenant result through the HTTP adapter with real `curl` requests, run the [multi-tenant Express demo](/guide/multi-tenant-demo); its API keys and task records are in-memory fixtures for local use only.

## Verify the permission matrix

```bash
pnpm exec tsx examples/policy-matrix.ts
pnpm check:tenant-demo
```

The matrix checks expected status, terminal policy, and handler execution for each case. The tenant demo additionally checks declared route-policy requirements and cross-tenant and ownership boundaries. Neither command needs real credentials or a running production service.
