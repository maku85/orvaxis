# What stopped the request?

Select a recorded request to see the policy decisions captured by Orvaxis, the terminal policy, and whether the handler ran.

<TraceExplorer />

The scenarios are **pre-recorded build fixtures generated by running the real Orvaxis request pipeline** in [`examples/policy-diagnostics.ts`](https://github.com/maku85/orvaxis/blob/main/examples/policy-diagnostics.ts). The site build checks their status, outcome, route template, and handler result before writing the static JSON asset. A test also checks that generated data omits request identities, headers, denial reasons, and private error text. The browser only selects a fixture; it does not call a backend or re-run policies.

These fixtures use demonstration requests and contain no credentials, request headers, resource IDs, free-form denial reasons, or raw error messages. The `broken` route intentionally throws inside its handler to demonstrate the safe error summary.

## Run the same requests locally

Clone the repository and install its development dependencies:

```bash
git clone https://github.com/maku85/orvaxis.git
cd orvaxis
pnpm install
pnpm exec tsx examples/policy-diagnostics.ts
```

The command runs the same three cases through `testRequest()` and prints the sanitized summary: an allowed request (200), a policy denial (403), and a handler error (500). To see the result through the HTTP adapter and try real curl requests, run the [multi-tenant Express demo](/guide/multi-tenant-demo); its API keys and task records are in-memory fixtures for local use only.

## Verify the permission matrix

```bash
pnpm exec tsx examples/policy-matrix.ts
pnpm check:tenant-demo
```

The matrix checks expected status, terminal policy, and handler execution for each case. The tenant demo additionally checks declared route-policy requirements and cross-tenant and ownership boundaries. Neither command needs real credentials or a running production service.
